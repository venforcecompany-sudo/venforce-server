3. DIAGNÓSTICO SECUNDÁRIO: 201 FALHAS DO AGENDADOR ("dateFrom e dateTo")
--------------------------------------------------------------------------------
Mensagem: "dateFrom e dateTo (YYYY-MM-DD) sao obrigatorios." (HTTP 400 de criarSyncRun).
Causa [FATO: código + TESTE LOCAL]:
  - central_vendas_sync_runs.date_from / date_to são colunas DATE NOT NULL
    (server/sql/central_vendas_schema.sql, ~linha 157).
  - O driver pg devolve um objeto Date (meia-noite LOCAL) para colunas DATE; não há setTypeParser global.
  - listarPeriodosNoturnosPendentes (server/services/centralVendas/centralVendasSyncRunService.js,
    linhas 354-386 em 1249d98) fazia String(row.date_from).slice(0, 10) => "Thu Oct 01".
  - criarSyncRun (mesmo arquivo, linha ~113) valida com /^\d{4}-\d{2}-\d{2}$/ e recusa.
  - A recuperação de boot (recuperarRodadasPendentes, centralVendasNoturnoService.js linha ~610)
    passa esses períodos para executarRodada; cada conta x período falha ANTES de criar run.
Por que nenhum teste pegou: o teste de recuperação usava um mock que já devolvia strings
  (server/tests/centralVendasNoturnoIdempotencia.test.js, ~linha 265).
Desde quando: 4600446 (2026-09-25). A recuperação de restart NUNCA funcionou em produção. [FATO: código;
  e nenhum run criado por recuperação foi identificado — mas ver D10 abaixo]
Impacto nos dados: nenhum — a validação falha antes do INSERT. [FATO: código; SQL não mostra run
  criado por esse caminho]
Origem das 201: compatível com 3 períodos pendentes (Q11) x 67 contas elegíveis (3 x 67 = 201).
  O número 67 NÃO foi confirmado (há 81 contas MELI ativas; elegibilidade = regra do scheduler). [HIPÓTESE forte]
  Também é uma HIPÓTESE (não verificada em log) que as 201 ocorreram no boot que se seguiu ao restart
  manual/deploy; o horário e o log do Render dessas falhas ainda não foram coletados. [NÃO VERIFICADO]
Segundo ponto afetado pelo mesmo padrão: sanitizeRun (linhas 83-84 em 1249d98) => run.dateFrom/dateTo;
  consumidor: server/controllers/centralVendasController.js ~linha 477 (iniciarOuRetomarMercadoPago
  Settlement). Provavelmente quebrado, sem uso observado (0 linhas em central_vendas_mp_settlement_reports
  na janela). [FATO: código; efeito exato NÃO VERIFICADO]
Latente (NÃO corrigido, de propósito): a função dia() em buscarRunAtivoDaConta usa toISOString();
  erra o dia em fuso a leste de UTC (Tóquio => 2026-09-30). No Render (UTC) não causa dano. [TESTE LOCAL]
Medição do parser real do pg (pg-types, OID 1082) em vários fusos, dia 2026-10-01:
  TZ                    getters locais   toISOString   String(Date).slice(0,10)
  UTC                   2026-10-01       2026-10-01    "Thu Oct 01"
  America/Sao_Paulo     2026-10-01       2026-10-01    "Thu Oct 01"
  Asia/Tokyo            2026-10-01       2026-09-30    "Thu Oct 01"
  Pacific/Kiritimati    2026-10-01       2026-09-30    "Thu Oct 01"
  Pacific/Pago_Pago     2026-10-01       2026-10-01    "Thu Oct 01"
Conclusão: getters locais = correto em qualquer fuso (adotado no hotfix de datas, ver 04_HOTFIXES).
O erro era um "freio involuntário": sem ele, o próximo boot dispararia a recuperação sobre períodos
obsoletos. Isso orienta a ordem do plano (06): fechar órfãos ANTES de publicar o hotfix de datas.
Correção de uma estimativa anterior: "~201 sincronizações no próximo boot" era só um TETO. O caminho
noturno usa reutilizarCompletedPublicado: true (criarSyncRun, linha ~171), então contas que já têm run
completed+published para a mesma tupla são REAPROVEITADAS, sem chamar o Mercado Livre. A carga real é só
das contas sem esse run; o pré-voo (F5) calcula isso.

7. VERIFICAÇÃO "RETOMADA APÓS RESTART SEM DUPLICAÇÃO" (item 6 do pedido do hotfix)
--------------------------------------------------------------------------------
Conclusão [FATO: código + TESTE LOCAL]:
  - Imports, pagamentos e repasses MP são gravados por sync_run_id; a leitura escolhe UM import published
    por conta x competência (maior published_at, cobertura contendo o trecho). Ads (ads_resumos_mensais,
    UNIQUE (cliente_slug, mes_ref, loja_campanha)) e o resumo do Cliente 360 (cliente_360_resumos_mensais,
    UNIQUE (cliente_id, competencia)) são upsert. Run interrompido nunca publica (publicarRun exige
    status completed e orders "complete").
  - Locks e vagas do Painel morrem com o processo (teste da seção 8 de painelContasPoolDeadlock.test.js).
Auditoria SQL confirma [FATO SQL]: 0 imports published de run não completed; 0 empates de published_at;
  0 linhas duplicadas de Ads.
Lacuna conhecida: um run MANUAL órfão em running só é reconciliado após RUNNING_STALE_MINUTES (60 min,
  centralVendasSyncRunService.js, reconciliarRunsStale ~linha 233); um clique nesse intervalo reaproveita
  o órfão e a conta sai "ignorada". Não dá para fechar órfãos manuais no boot com segurança (a Central
  também cria runs manuais; pode haver mais de uma instância).
